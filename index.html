Kubernetes 核心链路与底层依赖发现模型

1 Pod 实例与标签 (Labels)

Pod 启动并绑定元数据 Label。内部运行业务，IP 由 VPC-CNI 动态分配。

2 EndpointSlice 控制器

通过 Service Selector 动态搜索标签匹配的 Pod，并将其 IP 注入端点切片中。

3 Kube-proxy 与 流量网关

仅当 Pod 的探针成功（Ready: True）且位于 EndpointSlice 时，流量才真正放行。

4 EBS CSI 与 持久化存储

PVC 依赖 StorageClass 触发 CSI 供应，需具备 EC2 与 KMS 授权完成云盘加密挂载。

实战 Case 1：Service 选择器漂移引发的 503 幽灵故障

前端 UI 正常启动，但访问后端返回 503；Pod 全都在 Running，到底哪里断了？

表面现象 503 UNAVAILABLE
  • • 用户访问前端页面报 503 或 Connection refused
  • • kubectl get pods -n retail 显示所有 Pod 均为 1/1 Running
  • • 查看 Pod 日志一切正常，但流量就是进不去
真实根因 Selector 不匹配

Service 的 Selector 被误写为 retail-ui-canary，而实际 Deployment 产出的 Pod 标签为 retail-ui。 导致 EndpointSlice 关联实例数为 0（endpoints: null）。

service/retail-ui (YAML 差异对比) Key Fix: 1 Line Change
apiVersion: v1
kind: Service
metadata:
name: retail-ui
namespace: retail
spec:
ports:
- name: http
port: 80
targetPort: 80
selector:
- app.kubernetes.io/name: retail-ui-canary # 🔴 错误：找不到 canary 标签的 Pod
+ app.kubernetes.io/name: retail-ui # 🟢 正确：与实际 Pod Labels 保持一致

CloudShell / 命令行极速修复指令 

kubectl patch service retail-ui -n retail -p '{"spec":{"selector":{"app.kubernetes.io/name":"retail-ui"}}}'

实战 Case 2：就绪探针（Readiness Probe）404 导致滚动发布卡死

新版本 ReplicaSet 已产生，但 Pod 永远卡在 0/1 Running，发布超时被终止。

Events 关键报错 Probe 404
Readiness probe failed: HTTP probe failed with statuscode: 404

Kubelet 每隔 3 秒对容器发起 HTTP GET 探测，持续收到 404，因此 Pod 条件保持 Ready: False。

K8s 保护机制触发 发布暂停

Deployment 的滚动发布策略具有流量保护：新副本若无法就绪，绝不下线旧版本副本。超过 600 秒后触发 ProgressDeadlineExceeded 超时。

deployment.apps/checkout (Readiness Probe 修正) Path Correction
containers:
- name: checkout
image: public.ecr.aws/docker/library/nginx:1.27-alpine
readinessProbe:
httpGet:
- path: /healthz-not-configured # 🔴 错误：Nginx 默认 html 目录根本没有该文件
+ path: / # 🟢 正确：访问根目录返回 200 OK
port: http
scheme: HTTP

一键 JSON Patch 修复指令 

kubectl patch deployment checkout -n retail --type='json' -p='[{"op": "replace", "path": "/spec/template/spec/containers/0/readinessProbe/httpGet/path", "value": "/"}]'

实战 Case 3：EBS CSI 动态卷创建停滞与加密持久化存储故障

PVC 长期 Pending，Pod 调度报 VolumeBinding context deadline exceeded，如何打通 EBS CSI 与 IAM 最小权限？

PVC & 调度关键事件 ExternalProvisioning
[PVC]: Waiting for a volume to be created either by the external provisioner 'ebs.csi.aws.com' or manually by the system administrator.
[Pod]: running PreBind plugin "VolumeBinding": binding volumes: context deadline exceeded

Pod 等待持久卷绑定超时，PVC 停留在 ExternalProvisioning 阶段，底层云盘未能按声明自动生成。

真实根因全景 IAM / KMS 权限断裂

动态供应加密卷需要完整的三层闭环：
① StorageClass 声明 provisioner: ebs.csi.aws.com 且启用 encrypted: "true"；
② EKS Pod Identity 将 ebs-csi-controller-sa 绑定至专属 IAM Role；
③ IAM Role 策略必须具备 EC2 卷管理权限以及加密所必需的 KMS 授权（如 kms:CreateGrant、kms:GenerateDataKeyWithoutPlaintext）。若缺少 KMS 权限，卷创建将被底层静默拦截！

IAM Role / EKS-06-EbsCsiRole 最小权限补全 EC2 + KMS Grant Authorization
{
"Version": "2012-10-17",
"Statement": [
{
"Effect": "Allow",
"Action": [ "ec2:CreateVolume", "ec2:AttachVolume", "ec2:DescribeVolumes", ... ],
"Resource": "*"
},
+ { "Effect": "Allow", "Action": [ "kms:CreateGrant", "kms:ListGrants", "kms:RevokeGrant", "kms:GenerateDataKeyWithoutPlaintext", "kms:DescribeKey" ], "Resource": "*" }
]
}

CSI 控制器与持久卷实战排查指令链 

# 1. 观察 PVC 处于哪个生命周期阶段（重点看 Events 报告）
kubectl describe pvc challenge-data -n retail

# 2. 验证 EKS Pod Identity 是否正确挂载至 ebs-csi-controller-sa
aws eks list-pod-identity-associations --cluster-name EKS-06-cluster

# 3. 检查 EBS CSI 角色是否具备加密所需的 KMS 权限
aws iam get-role-policy --role-name EKS-06-EbsCsiRole --policy-name EbsCsiRolePolicy

# 4. 验证卷状态是否已由 Pending 自动收敛为 Bound
kubectl get pvc,pv -n retail

AWS EKS 控制台排查 5 大黄金法则（必背避坑）

面对各类 Permission Denied 与只读界面时如何破局

1. 永远先筛选 Namespace！

控制台报 cannot list resource at the cluster scope 时，说明命名空间输入框留空了！竞赛/企业中常给子账号分配单命名空间权限，必须手动填入 retail 才能看到资源。

2. 界面无编辑按钮？善用内置 CloudShell

AWS 控制台对许多原生 K8s 资源是只读的。直接点击控制台底栏左下角的 `[ >_ CloudShell ]`，不仅自带 AWS CLI 与 kubectl，还能实现毫秒级精准 Patch。

3. 503 先看 EndpointSlice，不要急着重启 Pod

Pod Running 却 503 时，90% 是服务发现脱节。使用 kubectl get endpointslices -n <ns> 查看是否有 addresses，若为 null，立刻比对 Service selector 与 Pod labels。

4. 滚动发布停滞先查 Events

新 Pod 产生但副本数不涨时，kubectl describe pod 最后的 Events 会明确记录是 Readiness probe failed 还是 CrashLoopBackOff，看清状态码（404/500/timeout）再动手。

5. 存储卡死？分清三大阶段（Provision -> Attach -> Mount）

PVC 卡在 Pending 时看 Events：若报 ExternalProvisioning，问题在控制器与 IAM/KMS 权限；若 PV 已生成但 Pod 卡在 ContainerCreating，看 VolumeAttachment 与跨可用区（AZ）限制；若报权限拒绝，排查加密卷的 KMS 授权策略。
