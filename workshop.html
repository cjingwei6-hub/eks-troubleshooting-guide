01

简介与环境架构 (Introduction & Sample Application)

了解 EKS Workshop 的体系结构，以及官方贯穿全篇的“零售商店”微服务参考架构。

Amazon Elastic Kubernetes Service (Amazon EKS) 是一项完全托管的 Kubernetes 服务。官方工作坊围绕真实业务场景设计，核心参考微服务为 Retail Store Sample App (零售在线商城)。

Retail Store 微服务组件拆解

UI 服务 (ui)

前端用户界面，基于 Vue/Nginx 交付静态资产，负责与所有后端 API 路由交互。

商品目录服务 (catalog)

Golang 编写的高性能目录查询服务，后端使用 MySQL 数据库持久化存储商品清单。

购物车服务 (carts)

Java/Spring Boot 框架构建，使用 DynamoDB 或 Redis 存储用户的动态购物车会话。

结账服务 (checkout)

Node.js 构建的核心支付与结账网关，处理订单生成，是滚动更新实验的核心对象。

订单服务 (orders)

处理已提交订单流水，通过消息队列或写入 RDS/PostgreSQL 进行持久化留存。

静态资产服务 (assets)

托管商品高清图片与多媒体内容，常作为 S3 Mountpoint 或 EBS 存储实训载体。

快速部署官方微服务应用

在 EKS 集群中使用 Kustomize 声明式部署全套示例微服务：

# 查看并一键应用零售商店的微服务清单
kubectl apply -k https://github.com/aws-samples/eks-workshop-v2/manifests/apps/retail-store/sample-acc/?ref=main

# 检查所有微服务 Pod 的启动就绪状态
kubectl get pods -n retail -o wide
02

计算与存储核心底座 (Fundamentals: Compute & Storage)

托管节点组 (MNG)、Fargate 无服务器、EBS/EFS CSI 持久化存储与平滑版本升级。

托管节点组 (Managed Node Groups)

AWS 自动化托管 EC2 节点的配置、伸缩与补丁。节点升级时自动执行 Drain（排空）确保业务零感知，并自动配置标准优化 AMI 与 kubelet 参数。

AWS Fargate 无服务器计算

无需管理任何 EC2 虚拟机。每个 Pod 独享专属微虚拟机（MicroVM），基于内核级别强隔离，按 Pod 申请的 vCPU 和内存精确计费。

EKS 三大持久化存储方案实战

存储类型 AWS 驱动 (CSI) 访问模式 (AccessMode) 典型适用场景
Amazon EBS ebs.csi.aws.com ReadWriteOnce (单节点独占) MySQL、Postgres、Redis 等低延迟关系数据库与高 IOPS 负载
Amazon EFS efs.csi.aws.com ReadWriteMany (多节点并发读写) WordPress、代码共享库、机器学习共享训练数据集、多副本内容管理
Mountpoint for S3 s3.csi.aws.com ReadOnly / Append-Only 海量 PB 级训练数据、模型权重加载、分析作业日志归档
EBS 动态分配 StorageClass 典型配置 (gp3)：
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-gp3-sc
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer # 关键：等待 Pod 调度确定可用区后再创建 EBS
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
03

Karpenter 下一代极速弹性伸缩 (Karpenter Autoscaling)

告别传统 Cluster Autoscaler 节点组限制，秒级直调 EC2 Fleet，极致节省算力成本。

传统 Cluster Autoscaler (CAS) 依赖 AWS Auto Scaling Groups (ASG)，伸缩速度慢（通常需要 3~5 分钟）、机型配置僵硬。而 Karpenter 直接绕过 ASG，直接监听 API Server 中处于 Pending 状态的 Pod，直接算出最经济的机型并在 45 秒内 完成扩容！

Karpenter v1 (NodePool + EC2NodeClass) 标准定义 

apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"] # 优先使用高性价比 Spot 竞价实例
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64", "arm64"]     # 支持 Graviton ARM 架构
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized # 自动缩容整合：当集群碎片化时自动换用更小更便宜的机器
    consolidateAfter: 1m
04

VPC CNI 与应用网关 (Networking: VPC CNI & Ingress)

原生 VPC 容器网络、前缀委托、Pod 独立安全组与 AWS Load Balancer Controller。

不同于大多数 K8s 使用的 Overlay 覆盖网络（如 Flannel/Calico VXLAN），EKS 默认采用 Amazon VPC CNI。每个 Pod 都直接获取一个真实的 AWS VPC 内网 IP，享受原生 VPC 路由性能与全套网络安全能力。

前缀委托 (Prefix Delegation)

分配 /28 IP 前缀给网卡，大幅提升单节点 Pod 密度（不再受限于 EC2 辅助 IP 配额）。

自定义网络 (Custom Networking)

将 Pod 置于单独的私有子网/网段，宿主机节点位于另一子网，解决主 VPC IP 耗尽问题。

Pod 级安全组 (SGP)

通过 SecurityGroupPolicy CRD 将 AWS 安全组直接挂到单个 Pod，实现真正的细粒度防火墙。

AWS Load Balancer Controller 流量分发

通过官方控制器无缝接管外部流量：

  • ALB (Application Load Balancer)：声明 Ingress 资源，支持七层路径路由、Host 路由、自动申请 ACM 免费证书与 HTTP/2。
  • NLB (Network Load Balancer)：声明 type: LoadBalancer 的 Service，支持四层超大并发、静态 EIP 绑定与客户端真实 IP 透传。
05

企业级安全、权限与秘钥 (Security & Identity)

新一代 EKS Pod Identity、IRSA 最小权限、Access Entries 与 Secrets Manager 外部密钥注入。

身份认证的重大演进：Pod Identity vs IRSA

新一代：EKS Pod Identity (推荐) 最新标准

不再需要为每个集群配置 OIDC 身份提供商（IdP）。直接使用 EKS Pod Identity Agent DaemonSet，在 AWS 控制台或 CLI 将 IAM 角色绑定到服务账户，支持跨账号与标签会话策略。

经典方案：IRSA 长期支持

基于 OpenID Connect (OIDC) 联合身份认证。Pod 挂载投射卷（Projected Token），AWS SDK 自动使用该 Token 调用 sts:AssumeRoleWithWebIdentity 换取临时凭据。

集群访问控制：告别 aws-auth，拥抱 Access Entries

过去 EKS 依赖 kube-system/aws-auth ConfigMap，极易由于误修改语法导致整个集群所有管理员被锁在门外！ 现在，EKS 原生提供 Access Entries API，在 IAM 层面直接将 IAM 角色绑定到集群内置的访问策略（如 AmazonEKSClusterAdminPolicy、AmazonEKSAdminPolicy），并支持限制在指定 Namespace 范围内。

全景可观测性与成本治理 (Observability & Kubecost)

指标体系 (AMP/AMG)、Fluent Bit 日志汇聚、Container Insights 与细粒度成本核算。

AWS 托管 Prometheus (AMP)

完全托管的高可用时序数据库，免维护自建 Prometheus 的持久化盘与分片扩容烦恼。

AWS 托管 Grafana (AMG)

开箱即用的企业级可视化看板，原生集成 IAM SSO 登录与 CloudWatch、AMP 数据源。

Kubecost 成本优化

精确核算到每个 Namespace、Deployment、Pod 甚至 Label 的美元花销，提供资源超配削峰建议。

07

自动化流水线与 GitOps (Automation & GitOps)

以 Git 为单一可信源的声明式交付（ArgoCD / Flux），与 ACK 云资源声明式托管。

通过 ArgoCD 部署 GitOps 体系：业务研发只需向 Git 提交代码合并请求（PR），ArgoCD 自动对比集群当前状态与 Git 仓库的预期状态，完成自动同步与渐进式金丝雀发布。

ACK (AWS Controllers for Kubernetes)：

允许您在 Kubernetes 集群内像创建 Pod 一样，用 YAML 声明管理外部 AWS 云资源（例如直接定义一个 RDSInstance 或 S3Bucket），极大统一多云与混合基础设施管理体验。

官方实战故障排查全集 (Troubleshooting Masterclass)

全网最系统 EKS 疑难杂症：CoreDNS 丢包、ALB 502/504、Pod 探针死锁与节点 NotReady。

场景一：Service Selector 漂移导致 503 Service Unavailable (EKS-01 真题)

生产高发

故障表象：Pod 处于正常的 1/1 Running，业务进程没有任何报错，但外部或集群内访问 Service 的 ClusterIP 恒报 503 或 Connection Refused。

# 诊断步骤 1：检查 Endpoints 或 EndpointSlices
kubectl get endpoints <service-name> -n <namespace>
>> 输出发现 ENDPOINTS 为 <none>！说明 Service 未能匹配到任何后端实例。
# 诊断步骤 2：比对 Service Selector 与 Pod 实际 Labels
kubectl get svc <service-name> -o jsonpath='{.spec.selector}'
kubectl get pods --show-labels

修复方法：统一 Selector 与 Pod Label。执行 kubectl patch service <name> -p '{"spec":{"selector":{"app":"<correct-label>"}}}'。

场景二：就绪探针 (Readiness Probe) 404 导致滚动更新卡死 (EKS-02 真题)

发布门禁

故障表象：执行版本发布后，新的 ReplicaSet 已创建，新 Pod 永远处于 0/1 Running，10 分钟后 Deployment 报 ProgressDeadlineExceeded 超时。

# 诊断步骤：提取 Pod 最新 Events
kubectl describe pod <new-pod-name>
>> Warning Unhealthy: Readiness probe failed: HTTP probe failed with statuscode: 404

核心原理：Kubelet 探针未得到 200~399 成功响应，标记 Pod 为 Ready: False。K8s 滚动发布流量保护机制生效，禁止销毁旧版本副本，导致发布流程挂起。

场景三：CoreDNS 解析超时与延迟膨胀

故障表象：Pod 频繁偶发解析外部域名超时（5 秒延迟）。

根因剖析：Linux 默认的 ndots:5 设置导致应用每次解析域名时，会依次补全 .retail.svc.cluster.local、.svc.cluster.local、.cluster.local 进行多次无意义内部查询，打爆 CoreDNS。 最佳解法：部署 NodeLocal DNSCache，或在 Pod 中设置 dnsConfig.options: [{name: "ndots", value: "2"}]。

场景四：ALB Ingress 报 502 Bad Gateway / 未关联 TargetGroup

根因排查三板斧：

  1. 子网标签缺失：公网 ALB 所属子网必须打上标签 kubernetes.io/role/elb = 1，私网打 kubernetes.io/role/internal-elb = 1。
  2. 安全组未放通：Worker Node 节点安全组必须允许来自 ALB 安全组的入站流量。
  3. 模式不匹配：Pod 若使用 VPC CNI，推荐使用 alb.ingress.kubernetes.io/target-type: ip 直连 Pod，避免经过 NodePort 二次转发。
